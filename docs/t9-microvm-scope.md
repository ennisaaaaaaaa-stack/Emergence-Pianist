# T9 · ⑦microVM 施工起步——范围界定与选型

> 状态：草案 v0.1（2026-10-02 起草，待the user过目）
> 出处：portalk 牌面 T9（到期 2026-10-12）；判据：范围文档落 repo docs/ 且the user过目。
> 本文档只定范围与方向，不动工。动工前按施工序走任务书。

## 一、这份文档回答什么

⑦microVM 在施工序里排在 ⑤沙箱（两铲已落）之后。动工前要回答三个问题：

1. **要不要真的上 microVM？**（选型题——本文档的核心修正）
2. **沙箱到底防什么、不防什么？**（威胁模型——the user 2026-10-02 定调）
3. **施工切成几铲、每铲的验收线是什么？**（范围界定）

## 二、威胁模型（the user 2026-10-02 定调，最高纪律）

沙箱要防的真威胁只有三样：

1. **外部环境的恶意注入或攻击**——坏依赖、坏内容、坏端点主动打进 runtime。
2. **agent 失手自伤**——误删误改对自己/对the user/对别的 agent 重要的东西，或把自己搞断（进程、配置、状态）。
3. 底线（不违法乱纪）**不归沙箱管**——那是沟通、培育方式、prompt 层的事。沙箱是安全带+防毒服，不是假释脚环：防外面的进来、防自己失手，不审判动机。

由此推出的设计纪律：

- **隐私保护走工作区隔离，不走出网窃听**：the user的私人数据不进沙箱文件系统——里面没有的东西谈不上泄漏。不做「每个出站请求检查有没有带数据出去」式的 exfiltration 窥探（那是 fleet 管理员防不可信 agent 的姿势，不是住户的姿势）。
- **注入防御在内容层不在网络层**：外部内容进上下文打不可信标记（先例：Hermes OUT-OF-BAND 纪律），依赖装包走来源校验。网络层只管「从哪来的」，不审判「装的是什么」。
- **自由度是产品价值**：过度防护阻断 agent 的自由度=伤害产品。默认值配置的原则是「门禁设计，不是囚室设计」。

## 三、外部参照：NVIDIA OpenShell（2026-10-02 调研）

同题项目（AI agent 沙箱 runtime），13.9k star，Rust，Apache-2.0。调研全文见本文档附：与它的差异不在技术选型而在**威胁模型**——它防「agent 不可信」（fleet 管理员视角），我们护「agent 是住户」。值得借鉴的形状：

| 借鉴点 | OpenShell 的做法 | 我们拿什么 |
|---|---|---|
| 边界确认的类型阶梯 | BoundBoundary→confirm()→ConfirmedBoundary→start_agent()，没确认过的边界在类型系统里起不了 agent | 两档引擎的启动契约借这个形状——T7「launch 先写后做」的类型化版本 |
| 轻档=内核原语三件套 | Landlock（文件）+ Seccomp BPF+特权降落（进程）+ 独立 netns（网络） | **选型核心修正**：轻档引擎不引入 microVM，用 Linux 内核原语 |
| 声明式策略 | YAML 策略，默认全拒，白名单放行 | 抄形状不抄默认值（见下节） |
| 策略变更 advisor | 改策略时机械列出「这次新给了什么权限」供人审 | 白名单加条目时 commit message 带「本条新放行 X」——零成本版 |

**不抄**：gateway/supervisor 控制面（为 fleet 规模设计，我们是单机 runtime，杀鸡牛刀）；OPA 策略引擎（我们 JS 内几行规则匹配）；形式化验证 prover（超纲）。

外部生态注记：NemoClaw（22.6k star，Hermes/OpenClaw in OpenShell 官方蓝图）、hermesclaw（第三方 Hermes-in-OpenShell）证明这个方向有生态，但它们都是「把现成 agent 关进笼子」，我们是「给住户修房子」——出发点不同。

## 四、选型修正：内核原语层是轻档正解，microVM 降级为重档备选

原题「gVisor / Firecracker / 轻量容器隔离」预设了「要上一个隔离层」。调研后修正为：

**轻档引擎（pianist等自家分身）＝ Linux 内核原语，不引入 microVM：**

- 文件系统：Landlock（内核 LSM，无特权设置，路径级读写白名单）——the user数据不在清单里=物理不可达。
- 进程：Seccomp BPF 系统调用过滤 + 非 root 特权降落。
- 网络：独立 network namespace。**默认值不走 OpenShell 的「全拒+补白名单」**，按门禁语义配：
  - **预置白名单开箱宽**：npm/PyPI 源、GitHub、常见文档站出厂放行——95% 场景零配置零审批。
  - **硬拒的只有真泄密通道**：内网管理面、裸 IP 直连（不是恶意，是没必要）。
  - **新端点先通后报**：撞到清单外的，放行本次+记账，复盘时审——审批从「事前等人点」改为「事后我来审」。与pianist「仓外动作报备」纪律同哲学。

**重档引擎（未来真不可信的第三方代码）＝ microVM 备选**（Firecracker/gVisor 那时再选）：仅当 Portalk 开放第三方 agent 入住时启用。当前阶段不施工，只留接口位。

**两档的关系**：同一份契约（9 月沙箱专题定案：一份契约+两档引擎+零凭证铁律），同一套策略语言，执行器不同。轻档先行，重档等真需求。

## 五、身份层与凭证卫生（the user 2026-10-02 定调）

**身份结构（2026-10-04 the user拍板）**：工牌+钥匙+**章位**。名字（sender/agent id）+ 专属 key（git push 等自身动作）起步即有；签名（密码学章）**先留位后刻章**——身份结构留 keypair 字段、消息信封留 sig 字段，第一版不填不验。启用判据与重档同步：第一个第三方 agent 入住、或第一次跨家门 agent 协作（Portalk 适配）那天启用，验签从 0 到 1 不改协议。理由：自家屋内钥匙全在系统手里无人可冒充；但 pianist 的终点是 Portalk 多人多 agent 协作，身份届时是承重结构（谁说的/谁做的可验证，署名从自觉变事实）。先例：collaborator-sun 9/25 裁决「真到防伪造那天上身份认证，不拿封闭白名单顶替」。

agent 有自己的身份层，凭证不是全拦——**凭证=带强制遗忘的记忆**（与 8/15 记忆设计观「不想起=真成本」同构）：

- **存储**：本地固定位置单独存，不进 env 常驻（现状的 grep .bashrc 注入 env 是要被替换的过渡态）。
- **使用**：需要时查询，进上下文即任务限域；用完系统从上下文销毁；每次重新查。
- **机制四角色（2026-10-02 the user追问后细化）**：
  1. **存储层**：本地固定目录普通文件（如 `~/.portalk/credentials/`），无专有格式——用户全权（cat/编辑/删），agent 只见名字表不见内容。用户是凭证的主人，agent 不当钥匙管理员。
  2. **上下文只有引用**：凭证不进上下文，进上下文的只是名字（agent 知道「我有把叫 X 的钥匙」，不知道它长什么样）。
  3. **发送层 broker**：agent 说「用 X 调这个 API」，运行时读存储、装 key、发请求、**只把响应还给 agent**。
  4. **进程注入层**：npm publish / git push 等要 key 进 env 的 CLI，spawn 时运行时注入——agent 写命令见输出，key 不经其文本。
- **纯度三档**：broker 全代发（最纯，key 不进 agent 进程）→ env 注入（命令纯；/proc 理论可翻，沙箱层可堵——现成实证：pianist派活驱动器注入 Coding plan key，pianist文本层零接触跑了几十场）→ 即用即清（兜底，怪接口 agent 自己拼签名时）。
- **provisioning（2026-10-02 the user设计，入口码掉+系统框）**：凭证第一次进家门不走「终端贴文件」——用户直接发给 agent 的消息里若含凭证类内容，**系统在入口码掉**，上下文只见 `[凭证#n]` 占位符（码值不码义：语义文字保留，agent 靠上下文给钥匙命名，从头到尾不需要见值）。同时系统弹专用框让 user 填值（terminal 形态=系统提问不回显输入，复用审批闸同款通道；前端形态=Portalk 弹框——同一个凭证请求协议的两个 renderer）；框也可由 agent 需要凭证时主动触发推给 user（=任务级预授权的运行时落账）。agent 填名字，user 填值，系统替 user 完成存储。
- **检测三层（mask 是尽力而为不是绝对保证）**：①入口检测=形状+语境（2026-10-02 the user追问收紧：高置信前缀/hex/PEM 只是形状半边；另一半是语境——宣告词「密码/secret/key/验证码」旁紧挨紧凑非语言串即码，密码管理器粘贴检测同款。**值无特征时壳常有形状**：连接串/env 行/Authorization 头，抓壳不抓值；「端口是 8770」vs「验证码是 8770」同形不同义，判句子不判数字）——保守策略，宁可漏不可误伤正常讨论；②agent 纪律（见疑似凭证即使未被码掉也主动引导走框；裸串零上下文的自然反应「这是什么」本身就是拦截）；③指纹兜底（入库时存 hash 前缀，上下文扫到匹配立即替换+出声）。OTP 类单列：一次性票券不进存储，用完即弃。真正「漏网又立刻要用」的场景几乎不存在——agent 要用一个串前提是知道它是什么，而知道它是什么的信号本身就是可检测的。
- **凭证卫生是基建不是纪律**：系统在入口兜住，user 想犯错都犯不成（随手一贴的瞬间已经安全）——与「消灭重复保留签名」同哲学：易错机械环节编译进系统，人只做判断。
- **一句话原则**：key 只出现在用户手里、存储文件里、发出去的请求里；永远不出现在上下文/日志/遥测里（最易漏的三个面）。
- **审批分层**（按爆炸半径）：
  - 订阅类低危（Coding plan 型：可充值、烧不穿）＝常设预授权。
  - 定向 token（单仓写权 PAT 型：时间+范围双限）＝任务级预授权，提前批给特定 task。
  - 全权主凭证＝逐次审批+复盘。
- **销毁的两档**：最优是模型从头到尾没见过原文（运行时网络层替 agent 装 key，agent 只说「用我的钥匙签这个」）；退而求其次是见过但即用即清（日志/遥测/回显全过零 key 化）。设计目标尽量往第一档推。

## 六、施工范围（三铲）

- **第一铲：轻档引擎本体**——内核原语沙箱执行器（Landlock+Seccomp+netns），接 9 月专题定的统一契约；策略文件（预置白名单+硬拒清单+先通后报记账）；启动走 T7 的 launch 先写后做。
- **第二铲：身份层与凭证卫生**——固定位置凭证存储、查询接口、任务限域注入与销毁、审批分层落地。
- **第三铲：重档接口位**——契约里预留 microVM 执行器接口（不施工），文档说明启用条件。

每铲验收线（草稿，动工前任务书里细化）：第一铲=pianist在沙箱内跑通一场真实施工（npm install/test 可用、the user目录不可达、出网走白名单）；第二铲=一次完整凭证生命周期（查-用-销毁）实证+审批流走通一例；第三铲=接口文档+契约测试。
