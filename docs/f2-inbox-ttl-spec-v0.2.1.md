## 定位一行

编排器收件箱（runtime inbox）的过期语义：按天清、不吃隔夜粮、不无限回补——与 Moonshake day file 同款时间观（the user 10/18 拍板原话语义：「F2 收件箱——逾期清空语义拍板：与 Moonshake day file 同款，按天清不吃隔夜粮不无限回补；剩窗口参数值待选项」）。

## 背景（为什么要按天清）

收件箱现状是「送达=下次醒来必见」（session 硬切续接定案，10/7）——但没有任何过期机制：
- 交货单/讣告/审批卡在 inbox 里无限期滞留，无人消费就一直躺着
- F1 更夫上线后重拉自动消费了一部分，但停拉转人类的卡、跨日残留的审批卡（10/12-13 双发死卡污染复验的病根）仍靠人工清
- session 硬切续接的语义是「未完结任务自动重挂」——重挂的是任务不是消息；隔夜的消息（比如昨天的审批卡）对今天醒来的 session 是噪音不是信号

## 语义（拍板翻译成机械规则）

1. **按天清**：inbox 条目带 `day` 字段（落账日的 JST 日）。每天首 tick，`day < today` 的条目清理出队。
2. **不吃隔夜粮**：清理是删除不是转储——过期的交货单/讣告直接销账，审批卡过期=自动 deny（带 expired 标记，审批人侧可查）。**终态可达**：expired-deny 是写终态不是从名单上抹掉——等卡的消费方（重拉会话）轮询/拉终态时拿到的是 `denied (by=system-expired)` 决断行，不是空。卡消失了，但卡的下场看得见。
3. **不无限回补**：清理不触发任何「补发」「重派」逻辑。隔夜的东西死了就是死了——该补的活是 F1 更夫的事（它有 launches 表自己的账），不是 inbox 的事。两本账不混。
4. **窗口参数（正典：方案 A）**：自然日界（JST 0:00 一刀切）——the user 10/18 晚已拍 A。与 Moonshake day file 完全同构。B（24h 滚动窗）/C（分级）降级为 env 逃生门（见实现面 6），不作为默认路径。

## 钟屋（day 判定单点）

day 字段的写入（新条目打 day）与清理（day < today 出队）**必须共用同一座钟**——单一 `nowJstDay()` 函数，两处调用同源。禁止一处取系统钟、另一处算日界：写入与清理各持一把钟时，时钟 skew（实测 WSL 比 Windows 快 5 分 22 秒，#1083）会把跨界条目结构性卡死或提前收割。F3 的 emit 按日翻篇共用这把尺（两把刀一套钟）。

## 范围（先立墙）

**管**：runtime inbox（orchestrator 的 inbox 结构——交货单/讣告/审批卡三类条目）
**不管**：
- Hermes 侧通知（hearth消息、桌面推送）——那是另一个系统的账
- tickets.jsonl（infra 工单）——工单有自己的生命周期（open/closed/blocked），不按天清
- schedule store——F1 已定「schedule store 零改动」
- driver 侧收件箱（dispatch 线）——驱动器收车时自己收口，隔夜场景归 F1 验尸

## 实现面（施工时的六件，预估单分身一铲）

1. inbox 条目加 `day` 字段：**新条目由写入路径自动打 day（`nowJstDay()` 同源）**；存量旧条目（无 day）走**上线迁移一次性补打 day=部署日**——补打后次日起自然过期（不是当庭清杀）。**施工读法钉死为 A（迁移式），禁 B（运行时 fallback `entry.day ?? today`）**：B 读法下 undefined 条目每天都被视为 today，`day < today` 恒假，存量卡永不过期——而本 spec 的第一真实用户正是 10/12-13 那族跨日残留卡（动机与实现打架的缝，hui #1088 定读法）
2. 每天首 tick 清理钩子（挂 watchman 验尸之后同位置——同是「开机对账」家族）
3. 审批卡过期自动 deny（复用 /approvals/decide 形状，by=system-expired，note 落账）。**落户口**：by=system-expired 进 decision actor 枚举（与人类/agent 并列的新 actor 值），审计账（decide 落账行）与消费面（终态查询）同步认这个值——枚举里没有它的位置就等于黑工，deny 了没人认账
4. 清理本身记账（journal 一行：**清了几条、逐条记 id 与类型**——sched 名/审批单号，死了的可追溯，半无痕不许）
5. day 单点钟：`nowJstDay()` 单函数（语义「钟屋」节），写入与清理同源调用；测试可注钟
6. env 逃生门：`CONDUCTOR_INBOX_TTL=day|24h|tiered`（默认 day=方案 A；24h/tiered 为 B/C 逃生门），非法值 fail-fast

## 验收（可证伪）

1. 落一条 day=yesterday 的交货单进测试 inbox → 首 tick 后消失 + journal 有清理行（含该条目 id）
2. 落一张 day=yesterday 的审批卡 → 首 tick 后：①`approvals/pending` 查不到 ②终态查询返回 `denied` 决断行（by=system-expired），**不是空**——模拟等卡消费方拉一次，收到的是 deny 终态不是空手
3. day=today 的条目 → 首 tick 后原封不动（阴性对照：清理不吃当天的粮）
4. 清理不触发任何 spawn/重派：grep 落账行无 relaunch 字样 + **清理前后 state.watchman 零 diff**（更夫的账 F2 一笔不动）
5. env 三型可配（day/24h/tiered 各跑一遍清理判定），非法值 fail-fast
6. 假钟跨界（单点钟验证）：注入 skew 钟（写入用真钟、清理读假钟，或反之）→ day 判定不出现「刚写入即过期/永不过期」的死区——两处调用同源，测试直接验证 nowJstDay() 注钟后写入与清理给出一致判定
7. **存量卡补打（施工读法 A 的验收钉）**：落一条**无 day 旧形条目**（模拟 10/12-13 存量卡形状）→ 跑迁移（补打 day=部署日）→ 迁移当日不清（day=today 阴性对照）→ 首 tick 在**次日**跑 → 该条目被清 + journal 清理行含其 id。B 读法（无迁移、运行时 fallback）下本验收不可达——无 day 条目永活，这正是钉 A 的可证伪判据
